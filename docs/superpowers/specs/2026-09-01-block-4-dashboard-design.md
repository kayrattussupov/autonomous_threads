# DESIGN: Block 4 — Дашборд (Vercel)
**Дата:** 2026-09-01 · **Статус:** черновик, ждёт ревью
**Родитель:** [SPEC.md](../../../SPEC.md) §10 «Дашборд», §11 Блок 4 (T4.1–T4.3)

## 1. Контекст

`SPEC.md` уже описывает пять экранов дашборда и виджет расхода. На момент написания в репозитории нет ни одной строчки дашборда — есть только `docs/` и сама спека. Фундамент (Block 0/1: Postgres, `LLMClient`, Threads-клиенты, ReAct-харнес) реализован и влит в `main` (merge-коммит `f9e2074`), включая `src/api/main.py` — сейчас это только `GET /health`.

Три конкретных запроса пользователя:
1. Логи и трассировки работы агентов
2. Список запланированных и опубликованных постов
3. Комментарии от ИИ-аналитики

Все три уже покрываются существующими экранами спеки: (1) = экран «Агенты», (2) = экран «Посты» с фильтром по `status`, (3) = поле `rationale`, которое `analyst_agent` пишет при предложении стилевого варианта или правила playbook — оно всплывает на экранах «Стили» и «Playbook». Новых агентных возможностей это не требует — только чтение уже существующих полей.

Решено строить дашборд целиком (все 5 экранов + виджет расхода), а не узкий MVP.

## 2. Архитектура

```
Vercel (dashboard/, Next.js 15 App Router)
  Server Components / Route Handlers
        │  HTTPS, Authorization: Bearer <API_BEARER_TOKEN>  (только на сервере, в браузер не попадает)
        ▼
Caddy (:443) → FastAPI (src/api/main.py) → Postgres
```

Два новых куска, больше ничего не меняется:
- **Бэкенд:** `src/api/main.py` (или роутеры под ним) прирастает read-эндпоинтами и двумя approve/reject-эндпоинтами. Авторизация — тот же `API_BEARER_TOKEN`, что уже есть в `.env.example` (FastAPI-зависимость проверяет заголовок).
- **Фронтенд:** новый каталог `dashboard/` — самостоятельный Next.js 15 проект, деплой на Vercel. Все запросы к API идут из Server Components/Route Handlers, никогда с клиента — токен и `API_BASE_URL` живут только в переменных окружения Vercel.

## 3. Бэкенд: эндпоинты (T4.1)

Все — `GET`, кроме двух approve/reject.

| Эндпоинт | Возвращает | Экран |
|---|---|---|
| `GET /funnel` | посты → просмотры → ответы → диалоги → лиды, помесячно | Воронка |
| `GET /posts` | таблица `posts` с фильтрами `category`, `style_variant_id`, `model_used`, `status`; пагинация; медианы по группам | Посты |
| `GET /runs` | последние 50 `agent_runs`, свежие сверху | Агенты |
| `GET /runs/{id}/steps` | шаги `agent_steps` для одного прогона: мысль → инструмент → аргументы → результат → ok/fail → мс | Агенты |
| `GET /styles` | все `style_variants` (draft/active/retired), генеалогия через `parent_id`, `rationale` | Стили |
| `GET /playbook` | все `playbook_rules` со статусом, `rationale`, `evidence_n` | Playbook |
| `GET /spend` | `daily_spend` за текущий месяц (сумма) против потолка $10 | виджет расхода |
| `POST /styles/{id}/approve` | `draft` → `active`; сервер сам ретирует худший по медиане текущий `active`-вариант, с проверкой `posts_n ≥ 20` | Стили |
| `POST /styles/{id}/reject` | `draft` → `rejected` (новое значение статуса; колонка `TEXT` без `CHECK`, добавление безопасно) | Стили |
| `POST /playbook/{id}/approve` | `proposed` → `testing` | Playbook |
| `POST /playbook/{id}/reject` | `proposed` → `rejected` (уже валидное значение в DDL) | Playbook |

**Определение «диалога» для воронки.** В DDL нет колонки для этого понятия. Рабочее определение: строка `replies` со `kind IN ('question','objection')` и заполненным `responded_at` — то есть переписка, на которую мы ответили, считается состоявшимся диалогом. Это решение зафиксировано здесь, а не в коде без объяснения, потому что спека явно этого не определяет.

**Правило ретайра при approve стиля.** Логика ретайра («новый одобренный вариант вытесняет худший по медианному score», SPEC.md §7) и защита `posts_n < 20` реализуются на сервере, а не в UI — кнопка «Отклонить» на клиенте не может обойти это ограничение.

## 4. Фронтенд: экраны

`dashboard/` — Next.js 15 App Router, TypeScript, server components.

- **`/funnel`** (главная) — воронка по месяцам.
- **`/posts`** — таблица, фильтры по категории/стилю/модели, переключатель `scheduled`/`published` — закрывает пункт 1.2.
- **`/agents`** — список последних 50 прогонов; клик по строке разворачивает трассировку шагов инлайн (мысль → инструмент → аргументы → результат → время) — закрывает пункт 1.1.
- **`/styles`** — активные/предложенные/ретайренные варианты, генеалогия, `rationale` предложенного варианта, кнопки «Принять/Отклонить» — закрывает пункт 1.3 для стилей.
- **`/playbook`** — тот же паттерн для правил playbook — закрывает пункт 1.3 для playbook.
- Постоянный виджет в шапке на всех экранах: расход за месяц / $10.

## 5. Доступ к странице дашборда

SPEC.md фиксирует «аутентификация не сложнее одного токена» — это требование к API, а не к тому, кто может открыть страницу на Vercel. Публичный URL Vercel по умолчанию доступен всем, а на дашборде есть два мутирующих действия (approve/reject). Закрываем это собственной middleware в Next.js: один общий пароль в переменной окружения `DASHBOARD_PASSWORD`, простая форма входа, cookie на сессию. Работает на любом плане Vercel, не требует аккаунтов — тот же принцип «без аккаунтов», что и в остальной спеке, просто закрывает единственную дыру, которую спека оставила открытой.

## 6. Ошибки и граничные случаи

- API недоступен (Caddy/FastAPI лежит) → страница показывает явное сообщение об ошибке, а не пустую таблицу.
- `401` от API (неверный/просроченный `API_BEARER_TOKEN` в env Vercel) → отдельное сообщение, отличное от «API недоступен», чтобы не путать сетевую проблему с конфигурационной.
- Approve/reject на уже обработанном `id` (гонка: два клика, или другой человек уже принял решение) → эндпоинт возвращает `409 Conflict`, UI показывает тост и обновляет список без изменения статуса.
- Ретайр заблокирован (`posts_n < 20`) → `POST /styles/{id}/approve` возвращает `422` с понятным сообщением, UI показывает его вместо тихого no-op.

## 8. Вне scope этого дизайна

- Изменение схемы БД, кроме использования уже допустимых/новых строковых значений статуса (`style_variants.status = 'rejected'`) — новых таблиц и колонок не требуется.
- Мультипользовательский режим, роли, персональные аккаунты — общий пароль на весь дашборд, как и было решено.
- Экспорт данных, мобильная вёрстка, тёмная тема — уже вне scope по SPEC.md §10.
- Любая новая агентная логика — весь контент для дашборда уже пишется существующими агентами (`analyst_agent.rationale`, трассировка ReAct-харнеса и т.д.).
