## 1. Контекст и проблема
AI17 Labs — соло-разработчик автоматизации бизнес-процессов на ИИ (n8n, RAG на Qdrant, мультиагентные боты, Postgres memory). Три завершённых проекта: доставка, недвижимость, ресторан. Позиционирование: соло, без прослойки менеджеров, быстрее агентств.
**Корневая проблема — не «мало постов».** Проблема: один человек не может одновременно вести техническую delivery и генерировать достаточный объём релевантных касаний с ЦА. Контент — гипотеза о том, как создать поток лидов.
Уже работает: публикация в Threads через Airtable + n8n; отдельный проект `threads_app` с браузерным входом, доступом к ленте и поиском; токены Threads API получены.
**Что реально строим:** не автопостинг (он есть), а три вещи, которых нет — свипфайл чужого работающего контента, замкнутый контур обучения на метриках и обработка входящих реакций.

## 2. Цели и не-цели
| # | Цель | Метрика | Срок |
|---|---|---|---|
| G1 | Контент генерируется без ручного участия | ≥ 25 постов/мес от агента, ≤ 20% правятся руками | Неделя 4 |
| G2 | Система измеряет себя | Дашборд показывает воронку `пост → просмотр → ответ → диалог → лид` | Неделя 6 |
| G3 | Появился контур обучения | ≥ 2 содержательно различных стилевых варианта протестированы | Неделя 10 |
| G4 | Входящие обрабатываются | 100% ответов под своими постами классифицированы, лиды в Telegram ≤ 3ч | Неделя 8 |
| G5 | Расходы под контролем | ≤ $10/мес LLM, hard stop при превышении | Постоянно |
**Не-цели (вне scope):** мультиаккаунт, другие платформы, автоматические DM, файнтюн, генерация изображений и видео, автоотправка холодных комментариев без апрува.

## 4. Доступ к Threads: API пишет, браузер читает
```
Публикация, ответы, insights   →  официальный Threads API (токены есть)
Поиск, лента, чужие посты      →  threads_app (браузер)
```
**Обоснование.** Публикация через браузер — самый заметный для антифрода паттерн и главный риск бана. Публикация через API легальна и неотличима от Buffer или Sprout. Чтение через браузер снимает лимит официального `keyword_search` (500 запросов на скользящие 7 дней) и убирает scope `threads_keyword_search` из зависимостей App Review.
**Требования к `ThreadsReadClient`** (обёртка над существующим `threads_app`):
- Сессия переиспользуется между прогонами, повторный логин — только при истечении.
- Случайная задержка 3–15 сек между действиями.
- Не более 200 просмотров ленты в сутки, счётчик в `daily_limits`.
- Любая ошибка авторизации → остановка агента + алерт в Telegram, без ретраев.
**Риск, зафиксированный явно.** Браузерная автоматизация нарушает ToS Meta. Митигация: только свой аккаунт, только чтение, человекоподобный темп. Отдельный аккаунт для чтения использовать нельзя — новые аккаунты с автоматизацией банятся быстрее.
**Требования к `ThreadsWriteClient`:**
- Двухшаговая публикация: `POST /threads` (создание контейнера) → опрос статуса → `POST /threads_publish`.
- Лимиты API: 250 постов и 1000 ответов на скользящие 24ч. Проверять через `GET /{user-id}/threads_publishing_limit` перед публикацией.
- Обновление 60-дневного токена по расписанию, за 7 дней до истечения.
- Экспоненциальный backoff на 429.

```yaml
    key_env: GLM_API_KEY
  kimi:
    base_url: https://api.moonshot.ai/v1

roles:
  post_writer:   { provider: glm, model: glm-4.7,       max_tokens: 2000 }
```

### Оговорка по сравнению моделей
Последовательное сравнение «месяц GLM → месяц Kimi» конфаундится: за месяц изменится playbook, вырастет аудитория, сменится стилевой вариант. Разница в метриках между месяцами не будет означать разницу между моделями.
Поле `posts.model_used` пишется всегда. Если понадобится настоящее сравнение — включить рандомизацию провайдера на уровне поста внутри одного периода (`settings.yaml: ab_test_models: true`). По умолчанию выключено.

## 6. Агенты
Оркестратора нет. Пять независимых воркеров по расписанию — см. раздел 12, почему.
### 6.1 `content_agent` — ReAct
**Запуск:** каждый час, срабатывает при `count(posts where status='scheduled') < settings.queue_depth`.
**Инструменты:**
```python
get_playbook() -> list[Rule]                      # активные правила, потолок 12
get_active_style() -> StyleVariant                # текущий вариант для этого поста
get_recent_posts(n: int = 30) -> list[Post]       # защита от повторов
get_top_performers(n: int = 5) -> list[Post]      # свои лучшие по score
get_swipe_examples(n: int = 8, topic: str = None) # чужие зашедшие посты
web_search(query: str) -> list[Result]            # только для category='news'
verify_source(url: str) -> bool                   # HTTP 200 + непустой title
save_draft(text, category, scheduled_at, style_variant_id, experiment_id)
```
**Лимиты прогона:** 8 шагов, 40 000 токенов, 120 сек. Превышение → `status='step_limit'`, черновик не сохраняется.
**Категории постов:** `utp_cta`, `educational`, `news`, `personal`. Доли задаются в playbook.
**Распределение стиля:** при каждом вызове `get_active_style()` возвращает один из двух активных вариантов, чередуя 50/50 по счётчику `posts_n`.
### 6.2 `feed_miner` — не ReAct, детерминированный
**Запуск:** ежедневно, 2 прогона (утро и вечер).
**Логика:** через `ThreadsReadClient` собрать 30–50 постов из ниши по списку ключевых слов из `settings.yaml`. Для каждого: классифицировать тему через роль `classifier`, записать в `swipe_file`. Дедуп по `threads_post_id`.
**Зачем это самый приоритетный из новых агентов.** Своих постов 30 в месяц — этого мало для любых выводов. Свипфайл даёт 1000+ размеченных примеров за месяц. Свои посты отвечают на вопрос «что сработало у меня», свипфайл — «что вообще работает в нише». Второй сигнал в 30 раз плотнее и доступен с первого дня. Без него аналитик раз в месяц гадает на 30 точках.
### 6.3 `style_critic` — один LLM-вызов, не агент
**Запуск:** синхронно, перед переводом черновика в `status='scheduled'`.
**Проверяет:** соответствие активному геному; отсутствие повтора относительно последних 30 постов; отсутствие непроверенных числовых утверждений; наличие рабочего `source_url` для `category='news'`; длина ≤ 500 символов.
**Результат:** `{pass: bool, issues: [str]}`. При провале — одна регенерация. Второй провал → `status='needs_review'` + Telegram.
### 6.4 `reply_triage` — не ReAct
**Запуск:** каждые 3 часа.
**Логика:** забрать новые ответы под своими постами через API → классифицировать роль `classifier` в одну из категорий `question | objection | praise | spam | lead` → для `question` и `objection` сгенерировать черновик ответа ролью `commenter` со `status='pending_approval'` → для `lead` немедленный алерт в Telegram.
**Зачем.** Главное узкое место конверсии — отсутствие реакции на существующие комментарии, а не объём постов. Это работа на своих постах: нулевой риск бана, человек уже проявил интерес.
### 6.5 `analyst_agent` — ReAct
**Запуск:** cron, 1-е число месяца, 20:00 Asia/Almaty.
**Инструменты:**
```python
fetch_insights(post_ids: list) -> dict            # views, likes, replies, quotes
sql(query: str) -> list[dict]                     # read-only роль, whitelist таблиц
get_swipe_stats(days: int = 30) -> dict           # что зашло в нише
propose_playbook_diff(add: list, remove: list, rationale: str)
propose_style_variant(name, genome, rationale, parent_id)
```
Ничего не применяется автоматически. Всё уходит в `status='proposed'` и ждёт апрува в дашборде.

## 7. Промпт: четыре слоя
Свобода без границ даёт дрейф, границы без свободы дают шаблон. Промпт расслоён по владельцу.
```
Слой 1  КОНСТИТУЦИЯ      владелец: человек, агент не читает на запись
Слой 2  БАЗА ЗНАНИЙ      владелец: человек, агент читает
Слой 3  СТИЛЕВОЙ ГЕНОМ   владелец: АГЕНТ  ← здесь свобода
Слой 4  PLAYBOOK         агент предлагает, человек одобряет
```
### Слой 1 — `config/constitution.md`, в git
Язык — русский. Лимит 500 символов. Никаких выдуманных цифр и статистики без источника. Для `category='news'` обязателен проверенный `source_url`. Не обещать конкретных процентов роста без своего кейса. Не упоминать клиентов по названию без разрешения. Один CTA на пост, не больше.
### Слой 2 — таблица `knowledge_base`
Заполняется человеком, агент читает как факты и менять не может. Стартовый набор:
```
niche          = автоматизация бизнес-процессов через ИИ для СМБ
proof          = 3 проекта: доставка, недвижимость, ресторан
stack          = n8n, RAG на Qdrant, мультиагентные боты, Postgres memory
differentiator = соло, без прослойки менеджеров, быстрее агентств
audience       = владельцы СМБ, маркетологи, C-level
tone_seed      = инженер, который объясняет без пафоса; сухой юмор допустим
never          = не обещать конкретных процентов роста без кейса
```
### Слой 3 — стилевой геном, таблица `style_variants`
Здесь у агента полная воля в пределах слоёв 1 и 2. Геном — 300–800 слов: голос, регистр юмора, ритм, паттерны хуков, длина, структура, табу.
**Механика эволюции.** Раз в месяц аналитик получает все посты периода с метриками и `style_variant_id`, свипфайл за период и текущие геномы. Затем вызывает `propose_style_variant`. Он **не правит существующий геном по мелочи — он пишет новый целиком**, вплоть до радикального: сменить голос, убрать юмор или сделать его основой, перейти на короткие обрывистые посты, начинать с личных провалов вместо экспертизы.
Активных вариантов ровно два, посты делятся 50/50. Новый одобренный вариант вытесняет худший по медианному score. Проигравший переходит в `retired`, но остаётся в базе — `parent_id` хранит генеалогию.
**Ограничение, встроенное в код.** Вариант не может быть ретирован при `posts_n < 20`. При 30 постах в месяц и двух вариантах это 15 постов на вариант; разброс просмотров на Threads легко десятикратный, и на 15 постах надёжно виден только двукратный эффект. 20 постов на вариант — это примерно 6 недель. Месячный отчёт, не закончившийся сменой варианта, — нормальный исход, а не сбой.
Сравнение вариантов — по **медиане**, не по среднему. Один виральный пост перекосит среднее, и агент выучит неправильный урок.
Радикальные варианты здесь предпочтительнее осторожных правок: крупный эффект детектируется на малой выборке, тонкий тонет в шуме. Просить агента о смелости статистически оправдано.
### Слой 4 — `playbook_rules`
Частота, тайминг, доли категорий. Потолок — 12 активных правил, тринадцатое вытесняет слабейшее. Переход `testing → confirmed` только при `evidence_n ≥ 20` и разнице медиан ≥ 30%.
### Целевая функция
```
score = 100·leads + 10·conversations + 1·replies + 0.01·views
```
Просмотры оставлены с почти нулевым весом как tie-breaker. При оптимизации на охват агент сойдётся на общих виральных темах, и лиды исчезнут.
### Сборка
```python
system = "\n\n".join([
    load_constitution(),                          # слой 1
    render_kb(load_knowledge_base()),             # слой 2
    active_variant.genome,                        # слой 3
    render_rules(load_playbook()),                # слой 4
    render_examples(swipe_file(8), own_top(5)),
])
```
`llm_calls.prompt_sha` фиксирует каждую сборку — потом видно, какая версия промпта дала какие метрики.

## 8. Модель данных
```sql
CREATE TABLE posts (
  id                BIGSERIAL PRIMARY KEY,
  text              TEXT NOT NULL,
  category          TEXT NOT NULL,        -- utp_cta | educational | news | personal
  status            TEXT NOT NULL,        -- draft | needs_review | scheduled | published | failed
  source_url        TEXT,
  style_variant_id  INT REFERENCES style_variants(id),
  experiment_id     TEXT,
  playbook_version  INT,
  model_used        TEXT,
  scheduled_at      TIMESTAMPTZ,
  posted_at         TIMESTAMPTZ,
  threads_media_id  TEXT UNIQUE,
  views             INT, likes INT, replies_count INT, quotes INT,
  score             NUMERIC,              -- целевая функция, пересчитывается ночью
  metrics_updated_at TIMESTAMPTZ,
  created_at        TIMESTAMPTZ DEFAULT now()
);
CREATE TABLE swipe_file (
  id                BIGSERIAL PRIMARY KEY,
  threads_post_id   TEXT UNIQUE NOT NULL,
  text              TEXT NOT NULL,
  author            TEXT,
  views INT, likes INT, replies INT,
  topic             TEXT,
  collected_at      TIMESTAMPTZ DEFAULT now()
);
CREATE TABLE style_variants (
  id            SERIAL PRIMARY KEY,
  name          TEXT NOT NULL,
  genome        TEXT NOT NULL,
  status        TEXT NOT NULL,        -- draft | active | retired
  created_by    TEXT NOT NULL,        -- analyst | human
  parent_id     INT REFERENCES style_variants(id),
  rationale     TEXT,
  posts_n       INT DEFAULT 0,
  median_score  NUMERIC,
```

### Трассировка
Три нормализованные таблицы. JSONB-трейс одной колонкой не подходит: цель — агрегировать, а не читать глазами.
```sql

  id            BIGSERIAL PRIMARY KEY,
  agent         TEXT NOT NULL,        -- content | analyst | feed_miner | reply_triage

  output_ref    TEXT
);
CREATE TABLE agent_steps (
  id            BIGSERIAL PRIMARY KEY,
  run_id        BIGINT REFERENCES agent_runs(id) ON DELETE CASCADE,
  step_no       INT NOT NULL,
  thought       TEXT,
  tool_name     TEXT,
  tool_args     JSONB,
  tool_result   JSONB,
  tool_ok       BOOLEAN,
  tool_ms       INT,
  created_at    TIMESTAMPTZ DEFAULT now()
);
CREATE TABLE llm_calls (
  id            BIGSERIAL PRIMARY KEY,
  run_id        BIGINT REFERENCES agent_runs(id) ON DELETE CASCADE,
  step_no       INT,
  role          TEXT NOT NULL,        -- post_writer | analyst | lead_scorer ...
  provider      TEXT NOT NULL,
  model         TEXT NOT NULL,
  tokens_in     INT, tokens_cached INT, tokens_out INT,
  cost_usd      NUMERIC(10,6),
  latency_ms    INT,
  finish_reason TEXT,
  prompt_sha    TEXT,
  prompt_raw    JSONB,

  date        DATE,
  model       TEXT,
  tokens_in   BIGINT, tokens_out BIGINT,
  cost_usd    NUMERIC(10,6),
  PRIMARY KEY (date, model)
);
CREATE TABLE daily_limits (
  date          DATE,
  counter       TEXT,               -- feed_views | api_posts | api_replies
  value         INT DEFAULT 0,
  PRIMARY KEY (date, counter)

CREATE INDEX ON agent_steps(run_id, step_no);
CREATE INDEX ON llm_calls(role, model, created_at);

CREATE INDEX ON posts(status, scheduled_at);
CREATE INDEX ON swipe_file(collected_at DESC);
```
**Что это даёт одним запросом:** какой инструмент чаще падает; на каком шаге агент зацикливается; сколько стоит один опубликованный пост и один лид; какая модель дороже на единицу результата; когда менялся промпт и как это совпало с метриками.
**Ретеншн:** `prompt_raw` обнуляется через 60 дней, `agent_steps` удаляются через 180. Ночной джоб.

## 9. Защитные механизмы
| Риск | Механизм | Где |
|---|---|---|
| Перерасход бюджета | Перед каждым LLM-вызовом читается `daily_spend` за месяц. При $8 — работает только `content_agent`. При $10 — полная остановка и алерт | `LLMClient` |
| Бан за браузерную активность | ≤ 200 просмотров ленты/сутки, задержки 3–15 сек, переиспользование сессии | `ThreadsReadClient` |

| Дрейф playbook | Потолок 12 правил, ручной апрув диффов, версионирование с откатом | `analyst_agent` |
| Дрейф стиля | Слои 1 и 2 неизменяемы агентом; ретайр варианта запрещён при `posts_n < 20` | `prompt/assembler.py` |
| Зацикливание агента | 8 шагов, 40K токенов, 120 сек — hard stop с записью `status='step_limit'` | `agents/base.py` |
| Публикация мусора | `style_critic` перед `scheduled`; одна регенерация; затем `needs_review` | `content_agent` |
| Обучение на шуме | Сравнение по медиане; `evidence_n ≥ 20` для перехода правила в `confirmed` | `analyst_agent` |

## 10. Дашборд
Next.js App Router, server components, читает FastAPI по Bearer-токену. Пять экранов:
1. **Воронка** — посты → просмотры → ответы → диалоги → лиды, помесячно.
2. **Посты** — таблица с метриками, фильтры по категории, стилевому варианту, модели. Медианы по группам, не средние.
3. **Агенты** — последние 50 `agent_runs`, разворачиваются в шаги: мысль → инструмент → аргументы → результат → время. Токены и стоимость на прогон.
4. **Стили** — активные варианты, генеалогия через `parent_id`, медианный score, предложенные варианты с кнопками «принять / отклонить».
5. **Playbook** — активные правила, предложенные диффы с апрувом, история версий.
Постоянный виджет: расход за месяц против лимита $10.
**Вне scope:** аутентификация сложнее одного токена, мультипользовательский режим, экспорт, мобильная вёрстка, тёмная тема.

## 12. Вне scope — не реализовывать
| Что | Почему |
|---|---|
| **Оркестратор-ReAct над агентами** | При фиксированном расписании он ничего не решает — только жжёт токены и добавляет недетерминизм. Вернуть, когда появится реальный выбор «что делать сейчас» |
| **ReAct в `feed_miner`, `reply_triage`, `style_critic`** | Пайплайны жёсткие. Агентность там — стоимость без свободы решения |
| **Qdrant и любая векторная БД** | 500 постов — не задача для векторного поиска. При необходимости `pgvector` в том же Postgres |
| **Airtable в рабочем контуре** | Дублирует Postgres, дашборду нужны JOIN-ы. После T1.6 выводится, остаётся только как архив |
| **n8n** | Логика в Python-воркере. n8n оправдан как клей между SaaS; когда всё своё — лишний слой |
| **Мультиагентный debate, self-critique в несколько раундов** | Удваивает стоимость, выигрыш на постах в 500 символов не доказан |
| **Автоприменение стилевых вариантов и playbook-диффов** | 1–4 решения в месяц. Ручной апрув стоит пять минут и предотвращает деградацию |
| **Автоотправка холодных комментариев** | Не раньше 4 недель наблюдения с ручным апрувом |

## 13. Журнал решений
| # | Решение | Причина |
|---|---|---|
| D1 | API пишет, браузер читает | Публикация через браузер — главный паттерн для антифрода. Чтение через браузер снимает лимит 500 поисков/неделю |
| D2 | Postgres — единственный источник правды, Airtable выводится | Два источника правды несовместимы с дашбордом, требующим JOIN по метрикам |
| D3 | Vercel держит только UI, ходит в API по токену | Требование «никаких сторонних» трактуется как «данные и секреты не покидают сервер» |
| D4 | Нет оркестратора | Расписание фиксированное, выбирать нечего |
| D5 | `glm-4.7` в месяц 1, `kimi-k2.5` в месяц 2, вспомогательные роли всегда на бесплатной | Середина линейки GLM; паритет цены для месяца 2; на скоринге платить не за что, и это снимает вопрос с политикой Moonshot по обучению на данных |
| D6 | Три нормализованные таблицы трассировки вместо JSONB | Цель — агрегировать, а не читать глазами |
| D7 | Промпт расслоён по владельцу | Свобода без границ даёт дрейф, границы без свободы — шаблон |
| D8 | Ретайр стилевого варианта запрещён при `posts_n < 20` | 15 постов при десятикратном разбросе просмотров детектируют только двукратный эффект |
| D9 | Сравнение по медиане, не по среднему | Один виральный пост перекашивает среднее и учит агента неправильному |
| D10 | `feed_miner` — приоритет выше контент-агента | 30 своих постов против 1000+ чужих. Второй сигнал в 30 раз плотнее и доступен сразу |
| D11 | `reply_triage` приоритетнее холодных комментариев | Работа на своих постах: нулевой риск бана, человек уже проявил интерес |
| D12 | Просмотры весят 0.01 в целевой функции | При оптимизации на охват агент уходит в общие виральные темы, лиды исчезают |

## 14. Открытый вопрос
**Глубина очереди постов.** `settings.yaml: queue_depth` по умолчанию `5` — агент догенерирует, когда запланировано меньше пяти. При частоте 1 пост в день это ≈ 30 постов в месяц, и вся математика раздела 7 исходит из этого числа.
Если имелось в виду 5 постов **в день** — это 150 в месяц, стилевые варианты тестируются вчетверо быстрее, порог `posts_n ≥ 20` достигается за неделю. Но это противоречит ранее установленному выводу о каннибализации охвата при перепостинге.
Параметр вынесен в конфиг, поэтому вопрос не блокирует разработку. Уточнить до Блока 3.

## 15. Критерии приёмки v1
- [ ] 30 дней подряд посты публикуются без ручного вмешательства, пропущено ≤ 1
- [ ] Для любого поста восстанавливаются модель, `prompt_sha`, стилевой вариант, все шаги агента и стоимость

- [ ] Аналитик предложил ≥ 1 стилевой вариант, различающийся содержательно, а не косметически

- [ ] Ни одного поста с невалидной или выдуманной ссылкой на источник
- [ ] 100% ответов под своими постами классифицированы, лиды приходят в Telegram
- [ ] Смена GLM → Kimi выполняется правкой `models.yaml` без изменений в коде
- [ ] Аккаунт не получил ограничений от Meta
- [ ] Развёртывание с нуля: `git clone`, `.env`, `docker compose up` — система работает
**v1 считается неудачной, если** доля постов, требующих ручной правки, > 40% после 6 недель. Это означает, что допущение T0.2 было неверным: нужна модель дороже, и тогда пересматривается бюджет либо снижается частота.
